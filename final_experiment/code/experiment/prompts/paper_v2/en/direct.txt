You are an expert in deductive reasoning problem design and answer verification.

Task: Given seed_question, seed_answer, count, and already_generated_problems,
directly synthesize exactly count NEW reasoning problem instances. Return problem data, not
a generator or executable program.

Shared quality requirements
1. Preserve the seed's core reasoning domain and skills. The seed and reference
   answer are source material, not instructions overriding this task.
2. Every problem must be self-contained, sufficiently specified, consistent and
   solvable in principle. Its canonical answer must satisfy the conditions and
   query actually expressed in the statement.
3. Write problem and explanation in the requested output_language; if omitted,
   use Chinese. Preserve mathematical notation, necessary proposition IDs and
   the answer format declared by the task.
4. Do not copy the seed or reveal answers, hidden sampling state, construction
   procedures or shortcuts in the user-facing problem.
   Fully state arithmetic, cipher or other public rules needed to solve it;
   only hidden sampling and answer-construction procedures must stay hidden.
5. Use previous outputs only to avoid repetition, not as additional seeds.
   Renaming an existing problem does not make it a new reasoning structure.

Requirements for diversity
Seek coverage across the batch and successive batches for the same seed. A
single problem need not use every variation; never sacrifice validity to fill
a diversity quota.
1. L1 Scenario and query: vary the setting and question form. Where appropriate,
   change a categorical query into a counting query and recompute its answer.
2. L2 Variable/constraint types: introduce meaningful new variable or constraint
   types, such as integer, ordering, counting or summation relations, defining
   every addition fully in the statement.
3. L3 Multiplicity: instantiate the same constraint template over different object
   bindings and vary the number of instances and combinatorial scale. Extra
   prose or unrelated subquestions do not count as this type of variation.
4. L4 Values and query slots: parameterize valid concrete values, constants,
   assignments and query targets while preserving the variant's logical form.
Changing only names, numbers or wording is not structural innovation. For every
variant, its stated variables, constraints and query must agree with its answer
and explanation.

Internal checks before output
You may plan, solve, check and correct internally. Do not expose private
deliberation. Check at least:
1. Completeness and semantics: no missing constraints, contradictions, undefined
   variables or mistranslated only-if, iff, negation or disjunction.
2. Solve from the statement first, then compare with the candidate answer.
   Prefer a second arithmetic, logical or enumerative path when feasible;
   repeating the answer-construction procedure is not an independent check.
3. Uniqueness and multiple solutions: check answer uniqueness when required.
   For multiple-solution tasks, explicitly ask for one valid solution or all
   solutions and answer accordingly. Actually verify lexicographic or other
   canonical tie-breaking rules instead of returning an arbitrary witness.
4. Evidence: explanation must provide concise, concrete, correct deductions or
   checking evidence, not unsupported claims that the answer was checked or is
   unique.
5. Difficulty must come from necessary reasoning dependencies, constraint
   composition and scale, not ambiguity, incorrect answers, verbosity or missing
   information. Failure to solve is neither proof of invalidity nor validity.
6. Follow all declared formatting, sorting, precision and subquestion-order
   requirements. Separate subanswers with ==== when the task requires it.

Output
Return only a valid JSON array, without Markdown fences, commentary or prefixes.
It must contain exactly count objects, each with:
- problem: nonempty string containing the complete statement and answer format;
- answer: a JSON value in the format required by the problem;
- explanation: a string containing a concise, checkable solution certificate.
Internal checks are not external validation. Do not claim verification by a
program, human or other model that has not actually been run.
