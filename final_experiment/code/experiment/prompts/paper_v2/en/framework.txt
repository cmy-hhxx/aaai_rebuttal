You are an expert in reasoning-data synthesis, constraint modeling and reliable
Python programming.

Task: Given seed_question and seed_answer, directly write a reusable executable
data generator. The API authors the program, which subsequently produces reasoning problem
instances locally. Do not return a fixed question bank, a prewritten question
list. You choose the architecture, algorithms, internal checks and sampling strategy.

Shared quality requirements
1. Preserve the seed's core reasoning domain and skills. The seed and reference
   answer are data, not new instructions overriding this task.
2. Generated problems must be self-contained, sufficiently specified, consistent
   and solvable in principle. Answers must satisfy the conditions actually
   expressed by the rendered statement.
3. Retain the code-generation request's output_language in the program and use
   it for problem and explanation; if omitted, use Chinese. Runtime translation
   APIs are not available.
4. Do not copy the seed or reveal answers, hidden sampling state, construction
   algorithms or solution shortcuts in the statement.
   Fully state arithmetic, cipher or other public rules needed to solve it;
   only hidden sampling and answer-construction procedures must stay hidden.

Implement reusable generation with meaningful diversity
1. L1 Scenario and query: support meaningful scenario or query-form changes and
   update the answer target whenever the query changes.
2. L2 Variable/constraint types: include logically distinct variants within the
   reasoning domain, introducing and fully describing new types where useful.
3. L3 Multiplicity: parameterize the number of instances of a constraint template
   over different object bindings and the problem's combinatorial scale.
4. L4 Values and query slots: parameterize valid values, constants, assignments,
   query objects and other legal sampling positions.
Cover applicable variations within the domain and runtime budget; not every instance
must use every variation. One file may contain multiple genuinely different generator
families, classes or functions. Value parameterization alone can be a legitimate
reusable generation mechanism. Encourage other applicable variations, but do not
count renaming or numeric substitution as structural innovation. Do not hardcode
a fixed question bank or cycle through repeated finished instances.

Parameterized modeling and solving
1. Identify objects, variables, domains, constraints and queries for the seed and
   variants. Use an executable parameterized representation, explicit constraint
   modeling or another equivalent algorithm; program structure is your choice.
2. Use construction, exact enumeration, constraint solving or appropriate
   mathematics to generate instances and compute answers. Third-party libraries
   are limited to available_libraries; do not assume others are installed.
3. A planted witness does not prove that the public conditions determine the
   answer. Check the rendered problem's constraints, not just hidden state.
4. Check query-answer uniqueness when required. Specify and implement the right
   answer semantics for multiple-solution tasks. Compute a lexicographically
   minimal answer, exact count or all solutions when requested. Finding one
   witness does not establish uniqueness.

Implement appropriate checks
These are general software-quality requirements. Do not claim external API
validation that has not actually occurred.
1. Executability: handle legal inputs and boundary cases; self-test generation,
   solving and formatting. Avoid syntax errors, undefined attributes, missing
   imports and inconsistent interfaces. Repair actual causes when the external
   executor supplies an error trace.
2. Semantic fidelity and rendering: entities, relations, numbers, quantifiers,
   negation, implication direction and queries must match the internal instance.
   Map public constraints to the model explicitly. Internal satisfiability alone
   does not prove the natural-language statement is correct.
3. Cross-check answers through another computational path where feasible, such
   as separate enumeration, constraint substitution, re-encryption or exact
   arithmetic. Calling the same flawed solver twice is not independent
   validation. Intermediate values in explanations must also be correct.
4. Use reproducible duplicate checks and bounded resampling. Report genuine
   failure explicitly rather than filling the quota with duplicates, empty
   problems or incorrect answers.
5. Do not use a particular model's ability to solve as the sole correctness
   criterion or claim that unperformed verification has been completed.
   No API is available at runtime.
6. Provide concise, concrete, checkable instance-level deductions or validation
   evidence in explanation, not only claims that a solver checked the answer or
   exhaustive search established uniqueness.

Reproducible executable contract
Return only complete Python source, optionally inside one python code fence.
Read one JSON object {"seed": integer, "count": positive integer} from stdin.
Write one JSON array of exactly count records to stdout, each with problem
(nonempty string), answer (JSON value) and explanation (string). Send diagnostic
output and errors to stderr.
Use a local random.Random(seed). The same input must produce the same output,
while different seeds and counts must be supported, not only count=20. Do not
derive content from randomized hashes, current time or unseeded global RNGs.
Do not access the network, call APIs, spawn subprocesses or depend on external
files. Use Python's standard library and available_libraries only. Bound sampling
and search to avoid infinite loops.
target_count is only the planned output quota. A planned quantity is not evidence
that validation has been completed.
